## 2. Problem statement (Sam's test)

1. **Spatial faux pas (primary):** Living-room furniture is attractive and well-matched, but **main seating does not orient to the focal point** (TV/media wall, view, fireplace, art wall) and the sofa/armchair relationship doesn't form a correct conversation zone. The room reads as nicely-chosen pieces placed without a designer's layout logic.
2. **Missing planning constraint (secondary):** The clarifying flow **did not surface living-only vs combined living+dining**. This is a *pre-concept* planning fork: a combined space needs explicit zoning + circulation, a different role set, and a different focal-point treatment per zone. Asking it after generation is too late.
3. **Root insight:** Recommendation quality (PM-001) is now good; the gap is **composition/placement intelligence** — a layer of professional interior-design rules guiding (a) what we *ask*, (b) how we *prompt* the concept, (c) what we *check* in QA, and (d) what we *warn* the designer about. Today these rules exist only as soft prose (§1.6) with no focal-point selection, no orientation rule, no zoning for combined spaces, and no checkability.

## 3. Research questions

**RQ-A — Rule discovery.** What are the salient, defensible professional layout rules for living, living+dining, dining, bedroom, (and home office) rooms? Which are near-universal vs style/culture-dependent (Dubai villa/apartment context)? Capture sources.

**RQ-B — Machine/prompt-checkability.** For each rule, can it be (i) checked from data we have (dimensions, role list, focal-point intent), (ii) only assertable via prompt language, or (iii) only verifiable by vision QA on the render? Classify every rule into **hard-checkable / prompt-checkable / vision-QA-only**.

**RQ-C — Clarifying-question selection.** Which rules depend on user intent that we cannot assume (focal point, living-only vs combined, seating priority, must-keep-clear walls, existing pieces)? These become clarifying questions. Which should be **deterministic always-ask** vs **AI-generated conditional**?

**RQ-D — Concept-prompt guidance.** Which rules should shape the concept `generationPrompt` (orientation, conversation zone, rug anchoring, zoning) and how, given they must be *additive* language (§1.6) not a prompt rewrite?

**RQ-E — Render/layout QA.** Which rules can be verified post-render (seating faces focal point, traffic path not blocked, coffee table reachable) and how (vision model checklist, heuristic on declared layout intent)?

**RQ-F — Designer-facing warnings/assumptions.** Which rules, when uncertain or in tension, should surface as **assumptions** ("we assumed the TV wall is the focal point") or **warnings** ("seating may block the window — confirm")?

**RQ-G — Combined living+dining.** What zoning + circulation rules govern a single combined space (zone separation, rug-per-zone, circulation spine, shared vs separate focal points, traffic between entry/kitchen/seating/table)? How should the room-type model represent it without a schema change?

**RQ-H — Measurement dependence.** Which rules require reliable measurements (clearances, walkways, viewing distance) and should therefore be gated by the existing `fitConfidenceUsePolicy` (`measurement-intelligence.ts:213`) — i.e. only asserted/checked when measurement confidence supports it?

## 5. Rule taxonomy by room type

Each rule is tagged with a **check type** — `[H]` hard-checkable (data), `[P]` prompt-checkable (language assertion), `[V]` vision-QA-only (post-render) — and a **measurement dependence** flag `{M}` when it requires reliable measurements (gated by `fitConfidenceUsePolicy`).

### 5.1 Living room
- **L1 Focal orientation `[P][V]`:** Primary seating (sofa) faces/addresses the primary focal point unless the user specifies otherwise.
- **L2 Focal selection `[H-from-intent]`:** Focal point ∈ {tv_media_wall, view_window, fireplace, art_wall, conversation}. If unknown, default per blueprint (today's default = TV/media wall, `interior-design-language.ts:26`) **but record it as an assumption** (RQ-F).
- **L3 Conversation zone `[P][V]`:** Sofa + chairs form a conversation grouping (pieces address a shared center), not isolated display pieces.
- **L4 Chair orientation `[P][V]`:** Armchairs face or angle toward the sofa/conversation center.
- **L5 Coffee-table reach `[P][V]{M}`:** Coffee table reachable from primary seating (~30–45 cm gap). Numeric check only when measurements support it; otherwise prompt-assert.
- **L6 Rug anchors group `[P][V]`:** A generously sized rug anchors the seating group (front legs on rug, minimum size relative to sofa).
- **L7 Traffic path `[P][V]{M}`:** Main circulation does not cut through the conversation zone; keep ≥ ~75–90 cm walkways.
- **L8 Side tables / lighting `[P][V]`:** Side tables and lighting serve actual seated positions (reachable, paired where relevant).
- **L9 TV ergonomics `[P][V]{M}`:** If TV present, seating distance/viewing angle are sensible (≈ 1.5–2.5× diagonal; not extreme off-axis).
- **L10 View/window respect `[P][V]`:** If view/window is the focal point, do not block access/light unnecessarily; orient seating to share the view.
- **L11 Scale fit `[H]{M}`:** Anchor furniture footprint fits `wallLengthCm × roomDepthCm` with clearances (uses existing measurement fields).
- **L-align Seating alignment / orthogonality `[P][V]`** *(added 2026-06-01 from live QA — the "slanted sofa" regression)*: the primary sofa sits **parallel to the focal wall and square to the rug / room grid** — its back reads parallel to the TV/media wall, **not rotated diagonally** into the room. Angled placement is reserved for genuinely angled or open-plan architecture, and even then aligns to a clear room axis. **Sectional/L-shaped:** run the long section parallel to the focal wall with the chaise/return toward the room interior; never rotate the whole sectional off-axis. The coffee table aligns square to the sofa and focal wall; the sofa's front legs sit on the rug (reinforces L6). **Why this is distinct from L1:** L1 ("face the focal point") is satisfied by a diagonally-canted sofa — L-align constrains *rotation*, which L1 does not. The merged focal-placement guardrail (`interior-design-language.ts:9–15`, `livingRoomFocalPlacementGuardrail`) governs *which wall* and *that it faces*, but **not rotation**; L-align closes that gap. Implemented as **additive lines appended to that existing guardrail array** (do not fork the merged text), plus a vision-QA check (§8: "sofa back not parallel to focal wall / canted >~15° off the room axis"). Pairs with the PM-001 sofa size/silhouette discipline (§5.4): preferring a straight sofa over a sectional for rectangular single-TV-wall rooms removes the ambiguous shape that triggers the cant in the first place.

### 5.2 Combined living + dining (open-plan)
- **C1 Explicit zoning `[P][V]`:** Living zone and dining zone are visually distinct (rug-per-zone, orientation, lighting) yet cohesive.
- **C2 Circulation spine `[P][V]{M}`:** A clear circulation path connects entry ↔ both zones ↔ (kitchen if implied) without crossing either seating/table core.
- **C3 Focal per zone `[H-from-intent][P]`:** Each zone may have its own focal point (living → media/view; dining → over-table fixture/sideboard wall); resolve possible conflict (e.g. one TV wall serving both).
- **C4 Role-set union `[H]`:** Role list = living roles ∪ dining roles, de-duplicated, scaled to the combined footprint (don't double-rug a single small space).
- **C5 Back-to-back anchoring `[P][V]`:** Common device — sofa back can define the boundary between zones (console behind sofa), as long as it doesn't block circulation.
- **C6 Scale arbitration `[H]{M}`:** If the combined room is too small for both zones at full scale, downgrade supporting pieces and **warn** (RQ-F) rather than cram.
- **C-zone Deterministic hall topology `[P][V]`** *(added 2026-06-02 from live QA — "dining beside living, sofa down long axis")*: the shipped `living_dining` language says "two zones" but not *where* dining goes or that a divider is required, so renders place dining **beside** the living band and run the sofa **down the hall's long axis**. The deterministic fix — **living zone faces the TV wall; dining behind the sofa (or far end), never beside it; a divider (sofa-back console/screen) marks the boundary; one rug + one ceiling anchor per zone; single side circulation spine** — is specified as an additive `combinedHallZoningGuardrail` array in **`COMBINED_HALL_ZONING_FIX.md`** (with the exact draft lines, insertion points `interior-design-language.ts:37–44, 65–70`, and test spec). Operationalizes C1/C5/C2 deterministically; pairs with the §8 vision check.

### 5.3 Dining room
- **D1 Table centering `[P][V]`:** Over-table light centered on the table; table centered in the usable zone.
- **D2 Chair pull-out clearance `[P][V]{M}`:** ≥ ~90–105 cm from table edge to nearest wall/obstacle for seating/circulation.
- **D3 Chair count fits hosting `[H-from-intent]`:** Chair quantity matches implied household/hosting count (existing role quantity).
- **D4 Sideboard placement `[P][V]{M}`:** Sideboard/credenza on a wall with circulation clearance (existing blueprint `interior-design-language.ts:31–32`).
- **D5 Rug-only-if-fits `[P][V]{M}`:** Rug chosen only if pulled-out chairs still sit on it (existing language `:33`).

### 5.4 Bedroom
- **B1 Bed wall logic `[P][V]`:** Bed against a credible primary wall, ideally not under a window where it conflicts, with approach clearance on used sides.
- **B2 Bedside symmetry `[P][V]{M}`:** Paired bedside tables/lighting where space allows; both approach sides walkable (≥ ~60–75 cm).
- **B3 Rug under bed `[P][V]`:** Rug proportioned and positioned under/around the bed correctly.
- **B4 Circulation `[P][V]{M}`:** Clear path to door/wardrobe/ensuite; bed doesn't block openings.
- **B5 Window/curtain finish `[P]`:** Finished window treatment; don't block egress/AC.

### 5.5 Home office (secondary extension)
- **O1 Desk placement / sightline `[P][V]`:** Desk placed for a usable sightline (to door or window) and a credible video-call background.
- **O2 Task chair clearance `[P][V]{M}`:** Roll-back clearance behind the desk chair.
- **O3 Storage reachability `[P][V]`:** Shelving/storage reachable from the work position.

> **Rule-to-mechanism mapping (the deliverable shape):** every rule above resolves to one or more of: a **clarifying question** (§6), a **concept-prompt fragment** (§7.1), a **render-QA check** (§7.2/§8), or a **designer warning/assumption** (§7.3). Section 5.6 shows the structured form.

## 6. Clarifying-question recommendations

Goal: surface the **planning forks** before concept generation, captured as **structured `RoomDesignIntent`** (not free text), while respecting existing question caps and the AI-generated flow.

**Recommended deterministic always-ask (small, room-type-conditional set), asked before/at the top of the AI questions:**
1. **Layout mode (living rooms):** "Is this a living-only room, or a combined living + dining space?" → `layoutMode`. *(Directly fixes Sam's gap.)*
2. **Focal point (living):** "What's the primary focal point — TV/media wall, view/window, fireplace, art/display wall, or conversation?" → `focalPoint`.
3. **Seating priority (living):** "Should seating prioritize TV viewing, entertaining/conversation, family lounging, or formal hosting?" → `seatingPriority`.
4. **Dining-in-room (if layoutMode = combined or ambiguous):** "Do you need dining seating in this same room?" → `needsDiningSeating`.
5. **Must-keep-clear:** "Which walls/doors/windows must stay clear?" → `mustKeepClear`.
6. **Existing pieces:** "Are there existing pieces that must stay?" → `existingPiecesToKeep`.

**Design rules for the question layer:**
- Keep deterministic questions **few and room-type-gated** (e.g. focal/seating only for living; pull-out/hosting count for dining) so total question load stays within homeowner ≤3 / designer ≤5 norms — consider a separate short "planning" micro-step rather than inflating the AI question count.
- Each answer maps to a **structured field** consumed downstream (concept prompt + QA + warnings), unlike today's free-text answers.
- Where the user skips, **record an assumption** (RQ-F) instead of silently defaulting.
- The **AI clarifying generator** (`generateClarifyingQuestions`) should be told (later, additively) not to duplicate the deterministic planning questions.

**Research deliverable (Agent C):** exact wording, ordering, room-type gating, skip/assumption behavior, and the answer→field map — without yet wiring the form.

## 8. QA / eval strategy

Mirror the established PM-001 eval pattern (`packages/domain/src/product-matching-evals.ts`) — a deterministic harness + fixtures + a manual evidence doc convention (`docs/Tracks/v2-commercial/product-matching-evals/manual-qa/`).

**Three layers of checks (matching §5 tags):**
1. **Hard checks (`[H]`):** Pure functions over `RoomFacts` (dimensions + role list + intent), gated by `fitConfidenceUsePolicy`. Unit-testable: scale fit (L11/C6), clearance (D2/B2/O2), role-union correctness (C4). Output `pass | fail | not_applicable | needs_measurement`.
2. **Prompt-checkable (`[P]`):** Assert that the composed concept language *contains* the required intent fragment for the given `RoomDesignIntent` (e.g. focal=view ⇒ language includes view-orientation). This tests the seam without changing runtime behavior — it inspects the assembled string.

## 10. Acceptance criteria

1. **Intent captured:** Living-room briefs ask and structurally store `layoutMode` (living-only vs combined), `focalPoint`, and `seatingPriority` (Sam's two gaps closed) — verified by tests, with assumptions recorded on skip.

7. **No regressions:** Existing concept/render behavior unchanged when flags off; lint + typecheck clean (`./node_modules/.bin/tsc -p tsconfig.json --noEmit`, `./node_modules/.bin/eslint .` from `apps/web`, plus domain package tests).

**Stretch (post-beta):** vision-QA rubric (S6), render-language seam, additional rooms' `[V]` automation, numeric viewing-distance/walkway enforcement when scan-grade measurements exist.

## 11. Stop rules and beta-safe reduced scope

**Stop and escalate to Chief Architect / Sam if any of these are required:**
- A **DB schema or generated-type change** (`packages/db/src/types.ts`) — e.g. wanting real `geometry_json`/`doors_json`/`windows_json` population or a new `room_design_intent` table. **Stop.** Use `design_briefs.structured_json` + the domain layer instead; if true geometry is unavoidable, that is a separate, post-beta track.
- A **broad prompt rewrite** of `interior-design-language.ts` or the concept/render system prompts. Only **additive** language functions slotted into the existing composition arrays are allowed, and only at/after S4 with explicit approval. **Stop** on any rewrite.
- A **change to runtime image-generation behavior** before S4 is explicitly approved (and S6 is post-beta). **Stop.**
- A **production deploy or controlled preview** as part of implementation. **Stop** — staging/local only.
- A rule that **requires geometric positions we don't capture** (exact door/window coordinates, true traffic-path solving). Downgrade to prompt-checkable + vision-QA + designer warning. **Do not** build a solver this phase.
- Deterministic questions **inflating** the question load past homeowner ≤3 / designer ≤5 norms without a separate micro-step. **Stop and redesign** the question surface.

**Beta-safe reduced scope (if time is short):** ship **S0–S3 + S5 (capture + hard checks + warnings) only** — i.e. *ask the right planning questions and warn on clear faux pas / scale problems*, without yet injecting spatial language into the prompt. This closes Sam's **clarifying-question gap** and gives designers warnings, while deferring the **concept-language seam (S4)** — the first behavior-affecting change — until it can be validated. The orientation fix (S4) is the highest-value but highest-risk slice; enable it behind a flag the moment its prompt-checkable + manual render QA pass.
