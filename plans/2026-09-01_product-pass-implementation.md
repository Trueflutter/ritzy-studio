## Objective

A homeowner uploads phone photos, describes a feeling, and gets directions that belong to her actual room; she asks for one change and only that changes; she confirms what the design contains, sees products that visibly match it, pays in AED under a credits plan, and buys from a list whose stock was checked last night. A designer does the same with a whole floor plan, switches modes in one click, and hits the paywall only when starting a second client room. Every step above is protected by tests and a vision critique harness before it reaches Bolaji.

## Approach

Ten slices, each independently shippable, ordered so the pipeline becomes trustworthy before the journey is re-skinned around it. Concept generation goes concept-first (no SKU anchors before approval) which un-blocks revisions; a canonical `room_design_spec` is extracted at approval and becomes the single contract that sourcing, swaps, rendering, and QA all reference, which is what makes concept-to-product visual fidelity enforceable (Ayo's Gate 1 condition). Sourcing turns on candidate images and hard role contracts; rendering gains planned multi-view coverage anchored to real source photos; the existing spatial QA gains teeth instead of being rebuilt. Billing becomes plan-plus-credits in AED via an append-only ledger, coordinated one change across Stripe, webhook, and migrations. The catalog gets a nightly refresh with per-SKU freshness and the source-level URL fix for the 2XL poisoning found in Phase 0. The alternative (rebuilding journeys first) was rejected because current intake already collects more than the pipeline consumes; correctness is not input-blocked, and a pretty journey around a wrong pipeline is the product we already have.

Orchestration extraction is scoped to exactly the stages the slices change (Gate 1 approved boundary): concept generation, revision, sourcing and list building, selection and swap, plus new credit accounting. Billing plumbing, auth, CRUD, and the durable render queue stay put.

S7. Credits and billing (AED)
18. Migration M4, in one coordinated slice with the code: `user_plans`; `credit_ledger` with entry types `grant | reserve | settle | release | expire | adjust`, `amount`, `job_id` (partial unique index on settling entries for idempotency), `grant_id` attribution, and `expires_at` on grants (monthly grants expire at the end of the following cycle per the approved rollover); backfill of active designer subscriptions into `user_plans`. Credits are modeled as LOTS: every `grant` is a lot with its own `expires_at`, and every `reserve`, `settle`, and `release` row carries an allocation to a specific lot (`grant_id`), so a settle against an expired Free lot can never bleed into a later monthly lot; available balance is the sum of remaining balances of unexpired lots, and the reservation RPC consumes eligible lots in expiry order. The protocol lives IN the database as a single SQL function that atomically takes `pg_advisory_xact_lock(user)`, computes lot balances, refuses at insufficient balance, and inserts lot-allocated `reserve` rows in one transaction (PostgREST auto-commits per request, so app-side lock steps would be meaningless); job success converts reserves to `settle`, failure writes `release`; two concurrent submissions from a balance of one produce exactly one reservation. Lazy expiry on read plus a nightly sweep writes `expire` entries per spent-out lot. Grant provisioning is idempotent by construction: every grant lot carries an immutable unique `source_key` (`free_signup_v1:<user>`, `invoice:<stripe_invoice_id>`, `room_pass:<checkout_session>`, `pack:<payment_intent>`), and one DB function with `INSERT ... ON CONFLICT DO NOTHING` serves both the M4 backfill of the approved Free 40 lot and new-account provisioning (profile-creation hook with lazy first-read fallback), so concurrent first reads, retried triggers, or backfill overlapping signup cannot mint duplicate lots. The Room Pass grants its bundled lot via its validated checkout event; SUBSCRIPTION credits are granted exclusively from validated `invoice.paid` events (unique `source_key` on invoice id), after validating livemode, exact price id, currency, amount, and the customer-to-user mapping. That mapping exists BEFORE money moves: checkout creation first writes the Stripe customer id and a pending `user_plans` row, so an early-arriving `invoice.paid` always resolves its user; `customer.subscription.*` events update entitlement status only, never write grants, and apply monotonically AND atomically: application is a single DB function that locks the `user_plans` row, persists a strictly ordered `(stripe_created_at, event_id)` cursor, and applies the update only when the incoming event orders after the cursor in the same transaction, so two concurrently delivered events cannot both pass a stale comparison and commit in reverse order (a late older update can never reactivate a newer cancellation; tested with a concurrent reversed-commit replay, not only sequential replay). Money tables ship locked down in M4 itself: RLS enabled on `user_plans` and `credit_ledger`, authenticated users can SELECT only their own rows, all direct writes revoked from `anon` and `authenticated`, provisioning is service-role only, and the reservation RPC is SECURITY DEFINER deriving its user from `auth.uid()`. Stripe test-mode products and prices created (Home 149, Studio 349, Pack 49, all AED; Room Pass 99 kept for beta cohort); webhook extended with the same idempotency and exact amount-currency validation per price.
19. Entitlement cutover covers the DB side, not just app callers: M4 `CREATE OR REPLACE`s `has_active_designer_subscription` to recognise `user_plans` (Studio) alongside the legacy USD plan key during transition, which transparently fixes its two DB consumers (the rooms BEFORE INSERT trigger `prevent_unpaid_designer_extra_room` and `can_access_room_commerce`), and `CREATE OR REPLACE`s `can_access_room_commerce` to include plan entitlements beside `room_unlocks`. App callers then move to the plan-aware domain service; legacy USD recognition is dropped in a later migration only after a query shows zero active legacy subscriptions. Settings Billing tab (plan ladder, balance, packs); paywall moments use the feature dark card; designer USD price retired after cutover.

S8. Catalog refresh
20. Migration M5 (`catalog_refresh_runs`, `products.last_seen_at`); nightly refresh as cron plus queue, mirroring the final-render pattern: a `vercel.json` cron entry at `0 20 * * *` UTC (00:00 GST; Vercel cron is UTC) hits the secret-guarded `/api/cron/catalog-refresh` route, which enqueues one message per enabled retailer to a new `catalog-refresh` queue topic consumed by `/api/queues/catalog-refresh` (new consumer route plus `experimentalTriggers` entry in `vercel.json`), so per-retailer runs at the adapters' 1 to 10s delays never fight each other. Each retailer's nightly page budget is derived from the consumer's `maxDuration` and its adapter delay, and the consumer is resumable: `catalog_refresh_runs` records a progress cursor (pages completed, last URL) after every page batch, and a queue redelivery resumes from the cursor instead of restarting, so the 60s-retry pattern cannot double a retailer's traffic. The nightly path does NOT reuse `runCatalogIngestion`'s destructive child handling: today's runner deletes all `product_dimensions` and `product_images` before reinserting per product through independent PostgREST calls (`packages/ingestion/src/runner.ts`), a sequence that cannot be atomic client-side; M5 therefore ships a single database RPC `upsert_product_with_children(payload)` that validates the complete payload and writes parent plus children in one transaction, and the queue consumer calls only that RPC, so a crash mid-run leaves every already-committed product complete and never a parent with erased children. Paid truth is frozen and migration-safe: M5 adds snapshot columns to `shopping_list_items` (name, unit price, dimensions, image URL, retailer URL captured at selection), payment finalizes the snapshot transactionally inside the same transaction that activates the entitlement, M5's backfill writes snapshots for EVERY existing paid entitlement from current product rows BEFORE the first refresh night is enabled, paid lists render exclusively from snapshots, and purchase immutability is enforced at the database, not by convention: payment marks the list version `purchased` and the room carries an explicit working-version pointer; a post-payment swap or re-source clones the purchased version into a new working version through one DB RPC (clone plus snapshot finalization in a single transaction), UPDATE and DELETE on purchased versions and their items are rejected by trigger for every non-service role, and the shopping-list page reads the purchased version for paid rooms rather than "most recently updated" (today sourcing deletes and reinserts the same list's items, which must become impossible against a purchased version; tested with re-source, swap, and direct authenticated mutation attempts after payment). A pre-run export of the touched retailer's rows and post-run invariants (products row count non-decreasing, child-row completeness per updated product, paid-snapshot immutability) guard every night. Additive upserts, per-SKU `last_checked_at`, `last_seen_at`, skip-and-alert on blocks; canonical image URL normalization at ingestion (2XL fix at source) plus a one-time additive normalization backfill of stored `primary_image_url` values (original preserved in a new column); per-SKU freshness rendering ("checked last night" or "checked N days ago") replacing group-level text; retailer visibility rule enforced: products render only for retailers in the refresh set.
21. Enrichment revival for tags and dimension sanity quarantine (`data_confidence`), additive only.

## Acceptance criteria

Pipeline
1. A room whose sourcing pool includes 2XL products generates successfully on `main` code (Phase 0 payload fixture passes through the sanitizer; live smoke on the walk room succeeds).
2. With Evolink unreachable (stub 500s), image generation completes via the OpenAI fallback path against `api.openai.com`, and the `ai_jobs` row records the fallback provider.
3. Every text or vision call aborts with a surfaced error within its configured timeout when the provider hangs (integration test with a stalling stub); no request runs unbounded.
4. Every succeeded `ai_jobs` row created by a full run has non-null `cost_estimate_usd`, including text stages and queue-path renders; a per-room aggregation query returns a total for the run.
5. `reviseConceptAction` (or its service) accepts a critique on a concept with prior catalog anchors: the critique row exists, a child concept exists with `revision_of` set, and no redirect fires before the critique insert (unit plus live).
6. On the five harness rooms, the revision check passes at 5 of 5: the asked change is present and the unchanged-region similarity check passes per the harness checklist thresholds committed in `scripts/critique-harness/checklist.md`.
7. Spec confirmation: after approval, `room_design_specs` contains every object class the harness detects in the approved concept image at the committed detection threshold, and the `/spec` screen renders one editable row per object.
8. Sourcing fidelity (Gate 1 condition): on all five harness rooms, every selected product passes the harness product-to-design consistency check (category equal, and visual similarity of render region to product image at or above the committed threshold); the chandelier-for-floor-lamp and swing-chair failures from Phase 0, replayed as fixtures, are rejected by the contracts.
9. A role with no qualifying candidates renders a visible missing-role row with reason and guidance in both matching and shopping list; the run completes; totals exclude the missing role ("6 OF 6" style false completeness cannot render when roles are missing: asserted by component test).
10. View coverage: for a TV-lounge spec, the generated view set includes at least one view containing the TV wall (harness view-coverage check); each view's camera matches its declared source photo anchor where one exists.
11. Spatial QA enforcement: a seeded failing render (fixture) triggers exactly one regeneration then, if still failing, an honest failure state; `spatialQaRegenerated` reflects it.

Journeys
12. J1 budget holds on the Playwright run, on the restated basis committed in `docs/ux/journeys.md`: from authenticated first arrival (post sign-in) to the concepts screen showing a direction, at most 8 required interactions and 8 navigation clicks, counted by the suite; the signup leg has its own budget of at most 5 interactions (name, email, password, confirm link, sign-in). The combined first-run start screen (step 17) and the name-only homeowner project form are what bring the count inside budget; the suite fails if either regresses.
13. Submitting brief details with zero measurements proceeds to questions; the concept carries visible assumption notes per §12.5; submitting with a validation failure of any kind re-renders with every typed value intact (asserted field-by-field).
14. Pressing Enter in a question textarea advances to the next question (Playwright keyboard test), and a literal "no" advances.
15. Whole-floor-plan upload (image and PDF fixtures) yields a detected-room list; confirming one fills editable measurements with `source = plan_extracted`; measurements remain optional throughout; the PDF path (client-side pdf.js rasterization) is demonstrated working on a Vercel preview deployment before the slice merges, not only locally.
16. Mode switch: an account with `intended_mode = both` switches homeowner to designer and back without logout (auth session unchanged, Playwright); designer-only surfaces follow the active context server-side; creating a personal room while in homeowner context does NOT consume the designer free client room (trigger test: designer with one client room and zero personal rooms creates a personal room, then still gets the client-room gate only at the SECOND client room).
16b. Free-grant provisioning: after M4's backfill, every pre-existing account's available balance is exactly the Free 40 one-time grant plus any plan grants (query assertion on the walk accounts); a freshly signed-up account shows balance 40 before any purchase; running the provisioning function twice for the same user creates exactly one lot (ON CONFLICT test on the source key); the day S7 ships, a pre-existing account can still run a revision without hitting an upgrade screen.

Money-table lockdown and context protection: with an authenticated (non-service) client, direct INSERT and UPDATE on `credit_ledger` and `user_plans` are refused and SELECT returns only the user's own rows (RLS test); an owner UPDATE attempting to change `projects.context` is refused while other project fields remain editable (column-protection test).

18. Designer second-room gate appears at the second room creation, in AED, and the first room reached presentation without any payment (Playwright J3).

Billing
19. Checkout completes for Home and Studio in Stripe test mode with `currency=aed` and amounts 14900 and 34900; the webhook activates `user_plans`; subscription credits are granted only by a validated `invoice.paid` (a replayed duplicate invoice event changes nothing, a `customer.subscription.updated` alone grants nothing, and an invoice with a wrong price id, amount, or currency is rejected and grants nothing: three explicit webhook tests); an `invoice.paid` delivered before any subscription event still grants correctly via the pre-checkout customer mapping, and an older `customer.subscription.updated` replayed after a cancellation does not resurrect the plan (out-of-order tests).

## Rollout & rollback

Ordering rules
- Every migration is additive and lands before the code that reads it (M1 before S2 code, M2 before S3, M3 before S5, M3b before S6, M4 before S7, M5 before S8). No migration drops or rewrites existing columns; the only destructive change ever proposed (dropping the old entitlement RPC) happens one slice after its last consumer switched, in its own migration, reversible by re-creating the function.
- `products` is never truncated or deleted from; the URL backfill writes the normalized value while preserving the original in a new column, so rollback is a single reverse UPDATE.
- Stripe: create new products and prices in test mode first; webhook code accepts old and new plan keys during the transition; the USD designer price is retired only after zero active subscriptions reference it (verified by query), and the retirement is a config change, not a data deletion. Production cutover follows a written runbook inside the S7 slice: create the immutable live-mode Price IDs, map them per environment as config, deploy the webhook that handles them BEFORE any checkout can expose them, validate `livemode` plus exact Price ID plus amount plus currency on every event, reconcile Stripe subscriptions against `user_plans` after cutover, and only then retire the legacy price.
- Provider routing ships env-first (dev), then production env changes ride the S0 deploy; `RITZY_RENDER_EXECUTION` and the signup allowlist are untouched.
- Catalog refresh enables one retailer for its first staged night, then the remaining three after a clean `catalog_refresh_runs` review; the kill switch is removing the cron entry (config-only revert).
- Each slice is a PR gated by `/implement` increments, `/review`, and the harness or Playwright evidence named in its steps; Phase 0 baseline screenshots are the visual regression reference for every UI slice.

Rollback
- Code: revert the slice PR; no slice leaves a schema in a state the previous code cannot read (additive-only guarantees this).
- Data: ledger and plan tables are append-only or status-driven; erroneous grants are corrected by compensating ledger entries, never by row deletion; refresh runs are observable per row and stoppable per retailer.
- Flags: new behavior behind config where risk warrants (visual sourcing candidate count, QA enforcement, harness gate), each with a documented off value that restores prior behavior.
